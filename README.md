# Llama 3.1 70B Inference Capacity on NVIDIA RTX PRO 6000 Blackwell

Throughput, latency, power and GPU activity across a 150-point load sweep with vLLM. Data, code and report.

**Who this is for:** engineers and capacity planners who deploy large-model inference on multi-GPU servers and want measured throughput, latency and power data for Llama 3.1 70B on four RTX PRO 6000 Blackwell GPUs (PCIe, TP=4).

Llama 3.1 70B (FP8 weights, BF16 KV cache) was served with vLLM 0.30.0 on four NVIDIA RTX PRO 6000 Blackwell GPUs (PCIe 5.0 x16, no NVLink, tensor-parallel size 4). The sweep covers 5 input lengths x 6 output lengths x 5 request rates, giving 150 load points of 100 requests each. Each load point was monitored with `nvidia-smi` and NVIDIA DCGM, and KV cache use was read from the vLLM server logs.

## Main findings

1. **Output length is the main factor.** As output length scaled from 128 to 10,240 tokens, elapsed time rose from 19 to 815 seconds, time per output token increased from 37.8 to 64.7 ms, and average power grew from 195 W to 304 W per GPU. Throughput peaked near 1,750 tokens/s for 1,000- to 2,000-token outputs, dropping 28% at 10,240 tokens.
2. **Memory-bound.** Though the GPU engine was busy 67–99% of the time, the tensor pipelines for matrix-multiply-accumulate were active only 6–15%, delivering 4–6% of the estimated dense FP8 peak. Memory activity (24–56%) consistently outpaced tensor activity. Execution was limited by memory traffic, inter-GPU communication, and scheduling overhead, not tensor-core operations.
3. **KV cache pool full at long contexts.** LLM reserved 85 to 86 GiB of each 96 GB GPU at startup; comprising about 17 GiB for weights and up to about 68 GiB for the KV cache pool. The pool filled as input and output tokens of all active sequences accumulated to 100% for 1,024-token inputs with 10,240-token outputs. That pool held about 78 sequences at the full 11,264-token length; beyond that, vLLM held up sequences until cache freed up.

The report gives the evidence, the caveats and the estimates (`paper/`). Please read its limitations before reusing any number.

## Reproduce the analysis

Tested with Python 3.12.3.

```
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/analyze_sweep.py --sweep-dir data/sweep_results --out-dir analysis --logs-dir logs
diff analysis/full_summary.csv data/full_summary.csv && echo IDENTICAL
```

This writes `full_summary.csv`, `latency_percentile_table.csv`, `vram_flatness_summary.txt` and five figures. Regenerated figures should match those in `figures/` in content. File size and fine rendering can differ between matplotlib builds.

## Reproduce the benchmark

`scripts/run_sweep.sbatch` starts the vLLM server inside a Slurm job, waits for it to respond, runs a warm-up, and calls `scripts/run_sweep.sh`, which loops over the grid, runs the monitors and writes the manifest. Paths in the scripts are placeholders and must be edited for your system. Benchmark environment: Ubuntu 24.04.4 LTS, NVIDIA driver 590.48.01, CUDA 13.1, Python 3.12, vLLM 0.30.0. Appendix A of the report describes the full procedure.

## Provenance notes

- The sweep script that ran wrote three DCGM peak columns one field off in `manifest.csv`. The manifest was repaired afterwards from the raw DCGM logs with `scripts/fix_manifest.py`, which also added the run-window averages `avg_sm_active`, `avg_tensor_active` and `avg_dram_active`. The manifest as first written is in `data/provenance/`. The analysis uses the fully parsed `dcgm_*` columns, which were not affected.
- `scripts/run_sweep.sh` is the corrected sweep script. The as-run copy is in `scripts/provenance/`.
- Host names, user names, account names, file-system paths, IP addresses and GPU identifiers were replaced with placeholders in all released files.
- `peak_output_throughput` is empty in `full_summary.csv`; the benchmark client did not record it.

See `DATA_DICTIONARY.md` for every column and unit.
